Vendor: Le Hoang Quang Trung (sole proprietor), Da Nang, Vietnam.
Security contact: support@trunkle.win
Version 1.0 — 13 October 2026. Reviewed annually, and after any security incident.

This page describes the security practices for this app. It is separate from the privacy policy, which describes what we do with personal data.

1. Security model

The app has no backend, no database and no network egress. It is a Forge Custom UI app whose static files are served by Atlassian's own infrastructure. Page content is requested from Atlassian's API, checked inside the user's browser, and the spreadsheet is built there too.

The consequence is deliberate and is the most important control in this system: there is no server of ours to breach, no database to leak, and no customer data at rest anywhere. Any security incident involving this app is therefore a question of code integrity or account access, not of a data breach.

We collect no analytics, no telemetry, no error reports and no usage statistics. We set no cookies. There are no user accounts. There is no AI model in this app, and no data is sent to any third party, because we hold none to send.

Support requests arrive by email. We ask customers not to send table contents with a report, and we do not need them in order to help.

3. Encryption

  • In transit: all traffic is HTTPS/TLS. The app's static resources are served over TLS by Atlassian, and its one API call goes from the user's browser to Atlassian's API over TLS. No part of that path involves us.
  • At rest: not applicable to customer data, because no customer data is ever stored by this app or by us.
  • Credentials used to publish the app are held in the vendor's own credential storage and are never committed to the repository. An automated test asserts that the shipped bundle contains no secrets.

4. Access control

  • Multi-factor authentication is enabled on the source-code hosting account and on the Atlassian account used to publish the app.
  • No third party has access to the source repository, the Atlassian partner account or the domain.
  • API tokens are created with the narrowest scope that works and revoked when no longer needed.
  • The app itself requests exactly one Atlassian scope, read:page:confluence, and is read-only. It cannot modify pages, and cannot reach spaces, users, attachments or any other Confluence data. This limit is enforced by the Forge platform.

5. Secure development

  • No release ships without the full automated test suite passing — 724 checks — plus a mutation suite in which 125 deliberate faults are injected one at a time, each of which must be caught by a test.
  • The user interface is built with DOM calls only: no innerHTML, no inline script and no inline styles. An automated test asserts this on every build, so the Custom UI content-security constraints cannot be weakened by accident.
  • Third-party code is kept to a minimum by design. The only direct runtime dependency is Atlassian's own @forge/bridge. The .xlsx writer is hand-written rather than taken from a library, specifically to avoid shipping third-party code into a customer's browser.
  • Changes are tested in the Forge development environment before any production release.

6. Vulnerability management

npm audit is run before every release and the results are recorded. A finding that cannot be fixed without a breaking change is documented together with an assessment of whether the vulnerable code is reachable in the shipped bundle.

Atlassian's Security Bug Fix Policy sets our remediation deadlines, and we treat them as hard commitments:

Reporting a vulnerability

Email support@trunkle.win, or raise a ticket in the Atlassian Marketplace Security (AMS) project. We acknowledge a report within one working day. Please include the steps to reproduce; please do not include customer data.

7. Incident response

A written incident response plan is maintained. Its commitments:

  • Contain first. On a suspected credential compromise, passwords are changed and all tokens and sessions revoked before anything else is attempted.
  • Notify without waiting for a fix. Atlassian is informed as soon as an incident is confirmed, through the AMS project. Affected customers are informed by email from support@trunkle.win once the impact is understood, and before the public knows.
  • Notifications state facts: what happened, when, which app versions, what data could have been affected, what the customer needs to do, and what prevents a repeat. No speculation, and no minimising.
  • Afterwards, the preventive change is written as an automated test wherever it can be, rather than as a resolution to be more careful.

8. What this policy does not claim

Stated plainly, because an overclaiming security policy is worse than none:

  • No security certifications. We hold no SOC 2, ISO 27001, or equivalent attestation, and we are not currently pursuing one.
  • No penetration test and no bug bounty programme.
  • No backups of customer data, because none is held.
  • No 24/7 response. The realistic response window is within one working day.
  • No separation of duties. The vendor is one person; there is no second reviewer on a code change. What reduces the risk here is the architecture described in section 1, not process.
  • The incident plan has not yet been rehearsed. The first annual rehearsal is scheduled; until it has happened, the honest answer to "do you test your incident plan annually" is no.

These are consequences of the size of the business, not oversights, and they are reviewed as it grows.
